## H01：四个官方执行器的身份与真实模型闭环（关键路径第一环）

**现状**：协议适配与版本锁定已完成（Codex app-server、Kimi Wire 1.50.0 实测、Claude 2.1.193、DeepSeek dsh 0.1.6-alpha.2）；Kimi 有真实 Teams 协作实测（0.9.0 记录）；Codex/Claude/DeepSeek 缺真实完整任务；生效配置回读、跨厂商共同任务缺失。

**前置依赖**：授权账户（各工具官方登录）；独立示例 Git 项目。**这是唯一需要用户提供资源的项。**

**实施步骤**：
1. `src/native_executor.rs` 的 `NativeResult` 增加身份回读字段：工具版本、精确模型、提供商、请求/有效 effort、账号渠道、证据时间戳；各适配器（`native_executor/claude.rs`、`deepseek.rs` 等）在握手后回读并填充，无法核验的字段保持 `None` 并显式标注。
2. Codex：补生效配置回读（app-server 的配置查询方法）→ 独立 Git 示例项目跑完整任务（规划→执行→验收），保存脱敏协议 fixture 到 `tests/`。
3. Claude/DeepSeek：各自用真实账号完成「只读检查 + 写入任务 + 权限批准 + 取消 + 失败注入」五类场景；结果记入 `docs/VALIDATION-0.12.0.md`（新建）。
4. 跨厂商任务：一个 Teams DAG，≥2 个厂商各承担不同节点，主机测试通过、源 checkout 不变；事件与被测 revision 归档。

**验收**：错提供商/错模型/错 effort 在提交前失败；无静默 API 回退；两厂商共同任务通过独立验收；每项实测有版本、任务、产物、测试证据。

## H03 剩余：正式 Automatic 派工（依赖 H01 + 计费解锁）

**现状**：决策内核完整（routing-v2：身份 attestation、榜单行、精确报价、峰谷条件、预算过滤、确定性排序、epoch 证据链）；预览/保存策略/重放三接口可用；**未接启动路径**；候选绑定未持久化写回；无决策后预占。

**实施步骤**（`src/team_service.rs`、`src/team_store.rs`）：
1. `TeamService::start` 对 Automatic 策略：刷新两快照 + 加载注册表 → `routing::decide` → 决策写 `routing_decision` 事件 → selected 时把绑定写回 Team 记录（`team_store` 增加绑定更新事务）→ 再进入现有受管启动流程；blocked 时保持 blocked 并把 reasons 写事件。
2. 解锁条件门：仅当 `account_billing::dispatch_blockers()` 为空且身份/榜单/报价全部 verified 才允许进入启动；否则按现有合同阻塞（**不得绕过**）。
3. 并发一致性：同一 Team 的启动互斥（现有排他检查延伸）；决策事件与绑定写回同事务。
4. 测试：决策确定性（同输入同输出）、刷新失败阻塞、绑定写回原子性、blocked 团队不可启动。

**验收**：可从保存的证据重现分配；每节点用自己的官方工具；未知条件阻塞；真实跨厂商成功实例（与 H01 第 4 步同一次实测）。

## H04：预算真正约束原生消费（依赖 H03）

**现状**：`team_store.rs` 已有整数微美元预留/结算账本与并发测试；未与派工/原生 usage 事件闭环；`budget_usd` 一律阻塞（诚实状态）。

**实施步骤**：
1. 费用归属定义：规划/执行/评审/重试/缓存/在途请求分别归到 attempt 级账目；估算值与提供商确认值分字段（`estimated_usd` / `confirmed_usd`）。
2. 派工前预留（routing 决策的 `estimated_cost_usd` 上浮一个显式安全系数）、终态结算/释放、崩溃重启对账（扫未结算预留）。
3. 原生 usage 事件：各适配器把官方工具报告的 token 用量映射到 attempt（Kimi Wire/Claude stream-json/DeepSeek ACP 均有 usage 载荷，逐个核对字段语义）。
4. 硬边界策略：工具无法保证 USD 上限时，该渠道标记「不支持硬预算」，UI 显示软预警——不承诺做不到的硬限制。

**验收**：并发/崩溃不重复预留不漏结算；无零价未知项；最坏在途消耗可解释；只有能证明兑现的限制才解除 `budget_usd` 阻塞。

## H05：恢复、重试、分叉与长任务稳定性

**现状**：增加了独立终态任务的 `duplicate`→新 Draft 合同（新 workflow ID，不复制原生 session/输出，必须手动启动）；Teams child 禁止脱离父团队复制。所有适配器 `resume/fork=false`（诚实）；服务重启把运行中任务标 `interrupted`，不会自动重试。

**方法**：先做合同再逐适配器实现——区分「继续同一原生会话」（需保存原生 session id + 工具版本 + workspace revision + 可恢复性检查）与「复制成新任务」「从失败节点重试」（现有 attempt 机制延伸）与「分叉历史」。注入测试：服务崩溃、断网、待批准中退出、进程残留、集成中取消。**只有实测通过的适配器才置 `resume/fork=true`。**

**方法**：候选（Kimi Node、MiniMax、MiMo、ZCode 等）逐个按 [DEVELOPER_HANDOFF 第 12 节](DEVELOPER_HANDOFF.md) 的八步标准接入：来源许可 → 只读协议研究 → 独立适配模块 → 绑定与生效检查 → 权限生命周期 → 离线回归 fixture → 官方程序检查 → 产品化。**身份种子同步扩充**：按 v1.1 的核验方法（官方定价精确名 + 榜单 byte-identical 行）逐条附证据。

**方法**：独立实验样例库（多语言多难度任务集），对比四种策略（单官方客户端 / 固定单模型 Teams / 指定多模型 / 自动策略）；保存同任务同测试、模型与工具版本、全部阶段费用、人工介入次数；重复运行后报告分布。**无证据不写「等效官方效率」「节省 X%」**。
