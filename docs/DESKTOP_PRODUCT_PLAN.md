# Wonderland 桌面产品建设方案

日期：2026-09-21
状态：产品与技术设计，尚未实现
关联：[多模型自主协作总方案](MULTI_MODEL_ORCHESTRATION_PLAN.md)

## 1. 产品定位与核心体验

Wonderland 是 Rust 编写的 AI 工作台，统一项目、对话、任务、应用、文件、终端、网页和交付流程。它应同时提供两种完整体验：让系统选择多模型团队完成任务；或由用户指定一个 AI，通过它自身的官方工具完成整项任务。

应用中心将 MiniMax Code、Kimi CLI/Code、Codex、MiMo Code、DeepSeek Harness、官方 Claude Code、ZCode 等纳入同一个工作区。各工具保留原生登录、模型执行循环、配置和升级机制，Wonderland 提供共同的项目入口、运行控制、产物与验收视图。

本方案把用户提出的“网站”解释为内嵌浏览、项目预览和网站交付管理；“远程控制”包括连接远程执行主机，以及从另一设备管理工作台任务。两项都列入正式产品范围，按阶段交付。任意电脑桌面的鼠标/键盘远控可作为后续专门适配能力，不能与任务远控混淆。

## 2. Work / Chat 与执行方式

Work / Chat 是场景选择，与模型选择、执行策略、权限范围分别建模。

| 场景 | 用户目标 | 主要界面 | 完成依据 |
| --- | --- | --- | --- |
| Chat | 问答、讨论、阅读文件、探索想法、整理资料 | 会话、附件、引用、应用选择、输出文件 | 回答和交付内容；不自动创建复杂任务图 |
| Work | 修改项目、解决问题、制作网站或文档、执行长任务 | 目标、计划、任务图/看板、变更、终端、验收 | 明确的交付合同及验收记录 |

Chat 默认使用指定 AI；用户主动选择“自动选模”时再执行权重计算。Chat 使用官方工具受支持的聊天/只读配置；无法落实聊天所需权限边界的工具不伪装成只读 Chat。附件类型、图像输入、网页能力按实际接口显示，不因统一输入框就宣称所有工具支持。

Chat 中的讨论可“转为 Work 任务”：用户看到继承的目标、选定文件、约束和来源；创建新的任务身份及权限合同。Work 也可以打开旁路讨论，讨论不会暗中改变运行任务。跨工具续聊通过可见摘要与附件引用建立新会话，不声称原生私有会话能无损迁移。

| 执行策略 | 行为 | 失败与变更 |
| --- | --- | --- |
| 自动协作 | 刷新 LiveBench/价格；规划、选择官方执行器，按需要拆分与并行 | 在合同和预算内换执行器、返修或重规划，所有选择留痕 |
| 指定 AI 完整执行 | 锁定模型、推理设置、官方工具及账号配置；规划、实现、模型评审和总结使用该配置 | 不自动跨模型升级；需要换模型时呈现原因与新方案，用户更改绑定后再继续 |
| 自定义团队 | 用户固定某些任务/角色的执行器，其余部分允许自动选择 | 固定节点不可被自动覆盖；自动部分仍须在线核验数据 |
| 直接使用应用 | 在应用中心打开原工具的集成会话或内嵌 CLI，由用户直接操作 | 如未通过托管接口运行，明确显示费用/权限/任务进度的观测边界 |

指定 AI 完整执行可以有多个步骤；不必强制一条无结构的长对话。确定性测试和 Rust 调度不调用额外模型。若官方工具内部会使用其他模型，必须能关闭或锁定该行为，才能标记“指定模型完整执行”；只锁定厂商或应用而允许内部选模的运行，应另外显示为“指定应用，模型由原工具管理”。

LiveBench 约束不扩大为阻止用户打开应用：用户直接指定模型时没有模型权重竞争，因此未上榜不阻止手动选择，但显示“未纳入自动路由评测”，不能伪造评分。托管的 Work 和 Chat 模型调用仍核验官方工具、模型身份、账号和适用价格；自动选择发生时每轮必须刷新 LiveBench。仅打开 CLI/网页不触发模型调用；用户在非托管 CLI 内自行发起调用时，不能承诺 Wonderland 能强制拦截每次计费或模型切换。

## 3. 桌面信息架构

```text
┌ Wonderland ─ Work | Chat ─ 项目/主机选择 ─ 全局搜索 ─ 待处理 ┐
│ 新建任务/对话 │  项目与应用标签页                            │
│ 收件箱       │  目标 / 会话 / 看板 / 文件 / 变更 / 预览       │
│ 任务 · 看板  │                                              │
│ 项目         │  中央内容区                    可折叠详情栏    │
│ AI 应用      │                               执行器/验收     │
│ 连接应用     │                               预算/来源       │
│ Pull requests│                                              │
│ 网站         │  终端 / 日志 / 测试 / 后台服务                 │
│ 定时任务     │                                              │
│ 插件与技能   │  当前项目 · 当前主机 · 原生会话 · 连接状态     │
│ 远程主机     │                                              │
└ 设置/账号 ───────────────────────────────────────────────────┘
```

导航可收起并按常用项固定；任务详情不把所有面板同时铺开。当前项目、主机和执行器在任务/会话标题附近持续可见，切换导航不改变后台运行任务的绑定。全局搜索覆盖任务、对话、项目、产物和应用；搜索结果尊重项目和连接权限。

一项任务可以拥有多个面板，但只有一个事实状态源。看板、时间线、任务图和应用页都是相同服务记录的视图，不能各自维护冲突的“完成”状态。

## 4. AI 应用中心：核心差异化功能

### 4.1 每个应用都应有完整入口

应用卡片提供图标、厂商、官方来源验证、版本、登录状态、支持模型、所在主机和集成能力。主要操作为“打开应用”“用它新建任务”“用它开始 Chat”；次级操作包括恢复会话、打开原生 CLI、配置、诊断、更新和卸载集成。

默认显示用户已安装和固定的应用，同时保留可安装目录。识别失败、未构建、版本不兼容、需要登录等状态有针对性操作，不能只给一个不可用按钮。

将四类对象清楚区分：

| 对象 | 含义 |
| --- | --- |
| AI 应用 | Codex、Kimi 等实际执行任务的官方工具 |
| 连接应用 | GitHub、文档、文件服务等可供任务访问的数据或操作连接 |
| 插件 | 扩展任务、面板、命令、连接器或执行器的安装包 |
| 模型/账号 | AI 应用可用的模型、订阅或 API 凭据配置 |

界面按用户任务组织，不将协议名作为主导航。高级诊断可显示 ACP、Wire、SDK、PTY 等实际接入方式。

### 4.2 在 Wonderland 中使用原应用的四种方式

| 方式 | 用户体验 | 实施要求 |
| --- | --- | --- |
| 原生协议工作区 | Wonderland 的界面展示原工具流式内容、工具活动、审批、文件和会话 | 调用官方结构化接口；模型执行仍由原工具完成，适合完整托管任务 |
| 原生 CLI 标签 | 在内嵌终端中使用工具自己的 TUI/命令，支持原有快捷键 | 复用 PTY；明确交互模式，不从屏幕文字猜测任务成功或完整费用 |
| 官方本地 Web 界面 | 工具提供可支持的本地 Web UI 时，在独立浏览器面板中打开 | 官方启动/会话接口、稳定 URL、登录隔离、生命周期管理经过验证 |
| 外部桌面应用 | 工具只有独立桌面窗口且无嵌入接口时，通过显式外部入口打开 | 标记“外部打开”，不伪称嵌入，也不把进程找到当作深度集成完成 |

目标是各家工具都能在 Wonderland 的原生工作区或 CLI 内实际使用；其中具备公开 Web UI 的可以保留其完整网页界面。**不能承诺把任何 Electron/Tauri/原生 EXE 窗口完整嵌入 egui。** 首先解决官方引擎及交互在应用内可用，不依赖跨进程强制挂接窗口这种脆弱做法。

原生协议会话与 TUI 是两种客户端。只有上游支持恢复/接管时才切换同一会话，且同一会话只有一个写入控制者。不能同时给同一 CLI stdin 或同一原生 session 从两个面板发送命令；不支持接管的工具明确显示“在同目录新开 CLI”。

### 4.3 首批应用范围

| 应用 | 目标集成 | 当前规划依据 |
| --- | --- | --- |
| Codex | 原生工作区、指定完整任务、自动团队、CLI | 沿用总方案已核对的官方接口，按安装版本验收 |
| 官方 Claude Code | 同上 | 官方程序与本地 Claude fork 分离，不能把 fork 标官方 |
| Kimi CLI / Kimi Code | 分别建立应用入口，可按同厂商分组 | 两套实现、入口指纹和能力独立登记 |
| DeepSeek Harness | 原生工作区、CLI、指定任务与团队 | 明确运行 profile，按 ACP/headless 能力验收 |
| MiniMax Code | 原生工作区、`mcode` CLI、指定任务与团队 | 本地 origin 指向 MiniMax-AI/minimax-code，README 明确公开 TUI/headless/ACP，未公开桌面应用源码 |
| MiMo Code | 优先 ACP 原生工作区、`mimo` CLI；按需适配其 HTTP 服务 | 本地 origin 指向 XiaomiMiMo/MiMo-Code；当前 Web 入口禁用，Web/App/Desktop 标为未维护，不能由 serve 推断可内嵌完整网页应用 |
| ZCode | 暂不纳入受管工作区；仅在用户已独立核验本地程序时保留手动终端候选 | 固定源码有自有 stdio/HTTP RPC，但根包和 CLI 包均 private，精确 npm 查询无发行物、GitHub 无 release；没有可验证的公开启动命令或版本摘要，详见 [ZCode 审计报告](WORK-REPORT-2026-09-23-ZCODE-AUDIT.md) |

`anytool/` 等本地目录作为只读参考/导入来源，不作为强制运行依赖。工具可以位于用户其他目录或远程主机；安装版和源码构建入口都有清晰版本身份。下载、构建和安装采用各工具支持的方式，完成后探测能力；更新不得修改正在运行任务的工具版本。

任何新增工具都须通过官方来源、协议、账号、实际模型、取消/恢复、权限、用量及产物测试后进入托管候选池。目录中存在源码不等于已安装，也不等于来源已经验证。

本次本地参考检查记录：MiniMax Code `e3724a13d72d`，MiMo Code `50cd713989f4`，ZCode `872ad960de7e`。这是来源配置与文档线索，尚不代表完成发行包签名/哈希验证或真实运行验证。MiniMax 另一个 `MiniMax-AI/cli` 项目主要是平台/媒体命令入口，不能将其当作编码 Agent 的替代品。

MiMo README 虽支持其他厂商账号和自定义 provider，托管任务仍遵守用户的模型→自身官方工具映射：OpenAI 任务交给 Codex，不能因为 MiMo 可以连接该账号就交给 MiMo 代执行。其余多 provider 工具同理。

适配前的已知差异：MiniMax ACP 当前声明不支持图片/音频输入，需要 `ask` 授权往返的任务走 TUI/ACP；MiMo 的 SDK 启动辅助函数仍有旧 `opencode` 命令/日志约定，不能假定可直接启动当前发行物；ZCode 的固定源码虽有初始 JSON 握手和自有二进制 RPC，但尚无可验证发行物，不能推断公开命令、权限默认值或网关模型回读。其 Computer Use 占位实现也不能作为已具备桌面远控的证据。

## 5. 新建任务、项目与看板

“新建任务”依次设置项目/目录、目标与附件、执行策略、执行器、交付与验收、预算和主机。常用值沿用项目配置，高级参数折叠；保存草稿、仅规划和开始执行分别有明确入口。模板包括问题修复、新功能、代码审查、研究报告和网站制作。

“指定 AI 完整执行”的主操作应直接展示模型和工具组合，例如“使用 Kimi Code 完成”。不能先显示用户选择 Kimi，实际规划阶段却自动调用另一个模型。

项目保存目录/仓库、语言和环境、任务默认值、连接、应用、规则、产物、网站预览及远程主机映射。项目级规则作用于新运行；运行任务使用启动快照。删除项目记录和删除磁盘文件是不同动作。

看板列建议为：待办、就绪、进行中、待处理、待验收、完成；失败/取消作为可筛选终态。卡片显示执行器、进度、阻塞原因、费用和关联 PR。拖动卡片表达用户意图，由服务校验转换；不能把卡片拖到完成就绕过验收，也不能拖动覆盖正在运行的 attempt。

运行进度显示已验收节点/总节点及当前阶段，避免猜测长推理的百分比。对小任务默认简单进度列表，多节点任务可切换依赖图，跨项目采用总看板。

## 6. 插件、技能和连接应用

插件中心支持发现、安装、启停、配置、版本锁定、更新与回滚，安装前展示来源、兼容版本和需要的能力。先做随产品验证的目录及本地导入，再建设公开市场。

建议 manifest 区分执行器适配器、MCP/连接器、任务模板、技能/命令、项目语言支持和界面扩展。执行代码优先隔离进程；轻量界面扩展使用受限声明式组件或隔离 WebView，不在主 Rust 进程中加载任意动态库。

不能假设 Claude、Kimi、Codex 或 ZCode 的插件格式相同。每个应用标示原生插件管理方式；能用上游管理接口的就调用原接口，不能无损转换的标明仅在原应用内可用。Wonderland 自有插件格式单独版本化，禁止为了“统一安装”而悄悄重写官方项目源码或用户原有配置。

官方插件市场可能同时分发官方及社区插件，维护者身份与来源按每个插件展示，不继承市场的“官方”标签。

连接应用按项目授权读写范围，凭据通过密钥引用传给适配器，不放入任务提示、日志或插件包。数据读取、外部发送、创建/修改远端对象是不同能力；用户可以预设允许范围，在范围内自动执行，避免每次普通读取都弹窗。

插件也不能更改模型与官方工具的硬映射。更新后的插件或执行器通过兼容检查后用于新任务，已有运行继续使用原版本。

## 7. 定时任务与后台运行

定时任务由 Wonderland 自己的 Rust 服务实现，不依赖其他桌面产品的定时器。用户从已有任务、项目模板或新目标创建一次性/周期任务，可指定自动团队或固定 AI。

每个计划保存时区、日历规则、下一次执行时间、项目/主机、执行策略、预算、允许动作、通知策略及停用日期。预览接下来几次运行时间，处理夏令时、休眠和主机关机后的漏跑策略。

默认同一计划不重叠执行；可配置跳过、排队或合并。触发生成独立 Run，由统一调度服务运行。用触发 ID 和事务去重，服务重启不会重复执行同一次计划。设置每次与累计预算，登录失效/审批等待不会自动扩大授权。

自动团队每次触发都刷新 LiveBench/价格；指定 AI 每次检查其模型/官方工具和价格。GUI 关闭但服务在线时可以继续；电脑关机不能承诺本机准时执行，需选择在线远程主机。失败、待处理和完成通知合并到收件箱，通知动作不等于再次派工。

## 8. 远程控制与执行主机

提供两个入口：桌面连接 SSH/配对的远程 worker 来执行项目任务；手机/另一电脑通过受认证控制界面查看和管理自己的 Wonderland 服务。首阶段功能为状态、日志、产物、暂停/继续/取消及有范围的审批，随后增加终端和文件交互。

远程 worker 使用 Rust，拥有远端进程、工作区和原工具。模型工具安装、账号登录和文件路径属于执行主机，不能拿本机已登录状态证明远端可用。密钥默认留在所属主机；文件显式同步或通过 Git/产物传输，并显示源与目标。

连接采用经过身份验证的 SSH 隧道或 TLS 配对通道，登记设备、主机身份、项目范围和可撤销会话。不能将现有仅供本机使用的 HTTP API 改为公网监听就称为远程产品。浏览器控制面需要独立认证、来源校验和会话过期策略。

断网后远端任务按启动合同继续或停止，重连按事件游标恢复，不能重复派工。对终端/会话写入采用控制租约；本机和远程两个操作者不能无提示同时输入。文件冲突、服务退出、休眠、凭据失效、设备撤销均有明确可恢复状态。

如后续增加通用桌面远控，另建屏幕流/输入代理、设备权限、可见控制状态和撤销机制；未实现前不将任务远控宣传成完整电脑远控。

## 9. Pull request 与代码交付

PR 中心按项目/仓库显示列表、分支、diff、讨论、检查状态、审查结果和关联任务。打开 PR 可以创建自动或指定 AI 的审查/修复任务；验收结果关联实际 commit，分支改变后标记旧评审过期。

支持从已验收任务准备分支、提交、推送和创建草稿 PR。先展示具体变更及测试证据，再按用户项目策略执行外部写入；用户已授权的发布/PR 操作不重复索要相同授权。

评论、提交审查、关闭 PR、合并和正式发布分别配置能力。合并前重新核对目标分支、head SHA、CI 与合并条件；不能把本地测试通过当作远端 CI 通过。GitHub 优先，后续 GitLab 等通过连接适配器扩展。

PR 审查也是模型任务，使用匹配的官方工具；外部 API 只处理仓库状态和交付动作，不代替模型执行。

## 10. 网站、浏览器与预览

网站中心包含收藏/会话标签、项目开发预览、生成的静态产物、已配置部署目标。用户可以打开网站作为参考，也可以从网站需求新建 Work 任务或将预览问题交给指定 AI 修复。

开发预览通过受服务管理的项目命令启动，记录 cwd、端口、进程、URL 和日志；支持停止/重启、响应式尺寸与错误查看。绑定到本地环回地址，远程预览通过受认证隧道呈现，不能因点击预览意外暴露公网端口。

Rust/egui 自身不是浏览器内核。增加独立的 Rust WebView host（Windows 可评估系统 WebView2）并通过受控 IPC 管理面板；布局、输入焦点、DPI、IME、剪贴板和生命周期先做技术验证。需要官方 Web UI 时走同一宿主，按应用隔离登录资料与数据目录。

普通网页、开发预览和官方应用 Web UI 使用不同信任域；网页脚本不能直接调用本地任务/文件/凭据服务。没有可信桥接合同的网页不开放特权 IPC。网页读取不自动授予提交表单、发送消息或部署网站的权限。

构建、预览和部署分开：部署使用已配置连接，生成可审查产物后执行预设授权流程；成功展示真实部署结果和 URL，不以开发预览 URL 冒充已发布网站。

## 11. 产品质感与易用性

桌面主体验使用统一设计系统：浅/深主题、清晰字体层级、稳定间距、细边界、适量留白和一致图标。官方应用图标使用可合法分发的官方资源或明确的文字标识；Wonderland 自有功能使用统一原创矢量图标。视觉稿必须覆盖真实异常状态，不能只美化首页。

必须设计欢迎/无项目/无账号/无工具状态；应用安装与诊断；Chat 和 Work；固定 AI 与自动团队；长任务和等待输入；看板；PR diff；插件；定时任务；远程断线；网站预览；结果交付。优先保证主路径，再逐步增加高级信息。

提供命令面板、搜索、最近使用、固定应用、键盘快捷键、面板大小记忆、布局恢复和收件箱。布局随窗口收缩时，将详情侧栏收起，不能通过缩小字体容纳所有内容。键盘可完成新建任务、选应用、查看产物和处理请求；中文输入与无障碍标签纳入验收。

## 12. Rust 服务和数据边界

核心服务、调度、权限、存储、进程、远程 worker 和桌面壳由 Rust 实现。各家 Node/Python/Go 工具以原进程运行，必要的 SDK sidecar 只负责协议适配。浏览器渲染来自系统引擎；这不改变 Rust 主工程的责任边界。

建议增加以下领域模块，不在一个桌面文件中堆全部功能：

```text
desktop/           模式导航、布局、命令面板、面板路由
app_registry/      官方应用目录、安装来源、能力、诊断、版本
sessions/          Chat/原生会话引用、面板绑定、接管租约
workflows/         任务与执行策略（复用总方案调度层）
projects/          项目配置、环境、主机路径与产物
plugins/           安装清单、兼容、能力、独立进程
connectors/        GitHub 等外部应用与授权引用
schedules/         时区、触发、去重、累计预算
remote/            配对、隧道、worker、重连与控制租约
reviews/           PR、diff、commit 绑定与验收
web_surfaces/      WebView host、预览服务、网站/部署记录
notifications/     待处理、错误与完成事件收件箱
```

应用会话、聊天、任务、项目、执行主机相互引用，不能只靠当前 GUI 选项确定运行目录。SQLite 增加应用安装、账号引用、会话关联、执行策略、插件安装、计划/触发、主机/设备、PR 关联、预览和通知实体；继续使用版本化迁移与事件记录。

`ExecutionPolicy` 至少区分 `AutoTeam`、`PinnedModel`、`PinnedApplication`、`CustomTeam`。面板的 `ViewMode = Work | Chat` 是另一字段。手动 CLI 会话单独标记 managed/unmanaged 和可观测能力，不在缺少证据时自动转成成功任务。

GUI、原生 CLI、npm 客户端共用后台任务状态。PR、定时器、远程客户端和插件均提交统一服务命令，不能各自开一套不可追踪的模型循环。

## 13. 分阶段产品交付

这是对总方案的桌面范围扩展。原有 14–21 人周只覆盖先前的核心范围，不能继续当作所有新增功能的总估计。新范围应在应用来源/接口和 WebView 验证后按具体模块估算，避免用一个未经拆解的日期承诺整个平台完成。

| 里程碑 | 交付内容 | 退出条件 |
| --- | --- | --- |
| D0 产品合同与入口验证 | Work/Chat、四种执行策略、全局导航；七类应用来源/接口清单；WebView 验证 | 确认内嵌/托管/外部模式及支持范围，完成关键界面设计和状态规格 |
| D1 可独立使用的工作台 | Work/Chat、新建任务、项目、官方应用中心、指定 AI 全程任务、终端、历史恢复 | 首批成熟适配器可以在应用内完成真实项目；固定 AI 不会暗中换模型 |
| D2 自主协作与七类应用 | 与总方案调度闭环集成；看板、任务图、数据刷新、预算、验收；逐个扩展全部指定应用 | 各应用按真实能力分别验收；自动与指定任务共享同一产物/状态，不能以“卡片已展示”算接入完成 |
| D3 开发交付流程 | PR、连接应用、网站/开发预览、插件/技能安装管理 | 从需求到代码/网站产物及草稿 PR 可走通；权限、更新和失败恢复有记录 |
| D4 持续工作与远程 | 定时任务、后台服务、远程 worker、另一设备控制、通知 | GUI 退出不丢任务；时区、漏跑、断网、重启、设备撤销不重复执行或串用凭据 |
| D5 发布与体验完善 | 七类应用兼容矩阵、性能、DPI/IME/无障碍、数据迁移、安装升级、文档 | 独立真实任务回归通过；功能状态诚实展示，桌面/CLI/npm 行为一致 |

总方案 M0–M2 与 D0–D2 共用任务，不另起重复调度器。界面贯穿开发：D1 就要有完成度较高的项目、应用、Chat 和单 AI Work 体验，不能等算法研究结束才开始做桌面。

## 14. 端到端验收场景

1. 从应用中心打开每个受支持工具，在内嵌面板中真实对话/操作；核对项目、模型、账号、工具版本和退出清理。
2. 选择 Kimi 或其他指定 AI，完成多文件任务，规划/实现/模型评审没有切换到其他模型；不合格工具明确说明限制。
3. 同一项目分别运行 Chat、指定 AI Work 和自动团队 Work，切换界面不串目录、历史、权限或预算。
4. Chat 转 Work 只继承选定内容；看板拖动不能绕过验收；自动调度遇到 LiveBench 不可用不使用旧权重。
5. 官方会话在协议面板与 CLI 之间恢复/接管时有单写入者；不支持的能力不出现伪按钮。
6. 插件更新失败可回滚，不损坏上游配置；连接应用的读授权不能用于未授权写操作。
7. 定时任务跨时区、休眠补跑和服务重启不重复；登录过期或超预算进入可处理状态。
8. 远程断线重连不重发任务；设备撤销终止控制权但按策略保留任务；本机/远端凭据与路径不混用。
9. PR head 改变使旧评审失效；生成网站、预览和部署状态可区分；网页不能访问本地特权桥。
10. 安装升级保留项目、会话和任务；真实长输出、大看板、缩放、中文输入和错误状态的界面可用。

本次只增补产品设计及总方案衔接，未安装工具、启动新任务、创建定时器、开放远程服务或发布产品。
